APPLICATION STRUCTURE / PALLETS

A small Python backend

FACT The Flask tutorial demonstrates registration, login, database access and changes to user-owned posts.

CHOICE Use Flask instead of a separate frontend framework plus API. Separate account, race and database responsibilities while limiting tools to learn. This is a scope decision, not evidence that Flask is universally better.

02

PRIVATE HISTORY / OWASP + FLASK-LOGIN

Signing in is only the first check

FACT OWASP recommends permission checks on every request. Flask-Login manages sessions but does not provide record-level permissions or registration.

CHOICE Require login, then query results using the authenticated user's ID. Compare this with filtering history only in JavaScript: a visual filter cannot enforce ownership. Test two synthetic users and direct requests to another user's record.

OWASP: authorization ↗ Flask-Login ↗Checked 2026-11-12 · Evidence: request permission checks; Flask-Login capabilities/exclusions · S1, S4, S5
03

PERSISTENCE / SQLITE

Save results beyond the browser

FACT SQLite's guidance includes low-to-medium traffic websites and discusses situations where a client/server database fits better.

CHOICE Start with server-side SQLite on persistent disk instead of browser-only storage or a separately administered database. Reconsider PostgreSQL for multiple application instances or heavy concurrent writes. Refresh and server-restart checks must establish persistence.

SQLite: appropriate uses ↗Checked 2026-11-12 · Evidence: websites and database-choice sections · S3, S4
04

TYPING INTERACTION / MDN

Check the text, not just the key

FACT MDN documents that the input event responds to user changes to a text field's value.

CHOICE Start from text input rather than keydown alone. Design explicit handling for deletion, paste and composition; an input event alone does not make a fair scoring system.

ASSUMPTION Physical-keyboard play is a suitable first target. Touch input and composition need separate checks before broader support is claimed.

MDN: input event ↗Checked 2026-11-12 · Evidence: description and text-control behavior · S2, experiment E1
05

ACCOUNT CHANGES / WERKZEUG + FLASK-WTF

Use maintained security helpers

FACT Werkzeug provides password hash generation and checking. Flask-WTF documents CSRF protection for forms and JavaScript requests.

CHOICE Use password helpers instead of plaintext storage, protect state-changing requests and verify the current password before a password change. Plan to revoke all user sessions after a password change, then require fresh sign-in.

RESPONSIBILITY SKETCH

The server owns the record.

The browser renders the race and immediate feedback. Flask identifies the user, validates requests and completion, then saves one owned result. The dashboard reads only that user's records.

Trust limit: Client input can be fabricated. Server validation and a server-recorded start time improve consistency; they do not prove a human typed honestly. Public competitive rankings are deferred.

Proposed records and scoring contract

Users: ID, login identifier, display name, password hash and scare settings. Sessions: revocable login records tied to users. Races: ID, user ID, passage ID, start/end timestamps, duration, correct and attempted inserted characters, mistakes, WPM and accuracy. Keep database files and secrets out of Git.

Draft project rules: WPM = (correct inserted characters ÷ 5) ÷ elapsed minutes. Accuracy = correct inserted characters ÷ attempted inserted characters × 100. Deletion does not erase earlier mistakes. Progress uses the corrected passage position.

Independent fixture: 250 correct characters / 260 attempts / 60 seconds → 50 WPM, 10 mistakes, 96.15% accuracy. Zero attempts and nonpositive duration need explicit handling. Arithmetic reviewed; scoring software not implemented.

04 / THE UNCERTAINTY

Does the scare help
or break the race?

Creative experiment E1 · Planned, not run. No evidence yet establishes that jump scares improve engagement.

A

Every mistake

Trigger a brief effect on each newly inserted incorrect character. Prediction: frequent errors may interrupt the task too much.

B

A short cooldown

Use the same effect, then wait three seconds before another can appear. Prediction: fewer interruptions may make completion easier.

Keep constant: passage, pacer, effect duration and input rules. Let an informed, willing peer try both versions; alternate order across participants. Record completion, mistakes, interruptions and a preference explanation. A small convenience sample can guide a design choice, not establish a general effect.

Stopping point & fallback

Limit the initial implementation spike to one study session. If effects are unpleasant or unstable, use a quiet visual mistake cue. Provide opt-in scares, independent sound controls, no flashing effects and a stop control. Exact duration and cooldown remain assumptions.

A small pattern experiment

Compare a simple conditional with function-based Strategy policies for mistake responses. Feed both the same timestamped error sequence; compare triggers, reset behavior, clarity and test effort. Keep the conditional if Strategy adds no useful separation.
